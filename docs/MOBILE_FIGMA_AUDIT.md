# 모바일 UI — Figma 정합성 진단 & 작업 추적 문서

> 이 문서는 `/mobile` 라우트(`src/components/mobile/*`)를 Figma 프로토타입(`Y'on Dashboard` 파일, "Mobile" 페이지, node `707:29096`)과 100% 일치시키기 위한 조사 결과와 진행 상황을 기록한다. 조사는 (1) 저장소 내 기존 Figma 추출 자료(`모바일개발용/`), (2) 현재 코드, (3) Figma REST API 실시간 조회(컴포넌트/variant/프로토타입 인터랙션) 세 갈래로 진행했다.
>
> **작업 범위 합의 (사용자 확정)**:
> 1. 레이아웃 버그 수정 + Figma에 정의된 신규 인터랙션(자동재생 캐러셀, 드래그 pull-to-load, 캘린더 스와이프 카러셀 등) 구현을 **한 번에** 진행한다.
> 2. Figma 프로토타입에서 연결이 비어있는 화면/탭(orphaned)은 **상식적인 제품 흐름으로 자체 보완**한다 (예: 리스트/캘린더의 아이템 탭 → 상세보기 열림, 하단 탭바 전체 탭 정상 라우팅).
> 3. **모든 컴포넌트는 반응형으로 구현한다.** Figma의 402×874 프레임은 고정 목업 1장일 뿐, §2.1에서 확인했듯 Figma 자체에 반응형 규칙이 없다 — 즉 "Figma와 100% 일치"의 의미는 "402px에서 픽셀 단위로 일치 + 다른 실기기 폭(360~430px 이상)에서도 비율이 깨지지 않고 자연스럽게 스케일링됨"이다. 이 문서 §4에 컴포넌트별 반응형 구현 원칙을, §5에 그 정합성을 정량적으로 검증하는 diff 워크플로우를 정리한다.

**이번 세션에서 발견 및 수정한 CSS 근본 버그 2건 (범위 밖이지만 화면 렌더링을 막고 있어 즉시 수정함)**: `globals.css`가 `@import "tailwindcss"` 뒤에 `@layer`로 감싸지 않은 채 커스텀 리셋 규칙을 작성해 두고 있었다. CSS Cascade Layers 규칙상 레이어 밖(unlayered) 규칙은 명시성과 무관하게 Tailwind의 `@layer utilities` 안에 있는 **모든** 유틸리티를 이긴다.
1. `a`/`button`/`input,textarea,select` 리셋 — 앱 전체 `<button>`/`<input>`의 `bg-*`/`border-*` 유틸리티가 전부 무력화되어 배경·테두리가 투명하게 렌더링되고 있었음. 새 navbar·캐러셀 버튼이 안 보이는 원인을 추적하다 발견.
2. `* { margin: 0; padding: 0; }` — **훨씬 광범위한 버그**로, 앱 전체(모바일+PC)의 `p-*`/`px-*`/`py-*`/`m-*`/`space-y-*`/`space-x-*` 유틸리티가 전부 무력화되어 모든 카드/버튼/리스트 행의 내부 여백이 실제로는 0이었다. 둥근 모서리(`rounded-*`)가 만드는 배경색 삼각형 틈이 착시로 "여백처럼" 보여서 여러 차례의 스크린샷 검토에서도 놓쳤고, 알림 전체보기 바텀시트의 높이가 비정상적으로 눌린 것을 조사하다가 발견했다.

두 규칙 모두 `@layer base { ... }`로 감싸 수정. 수정 전/후 스크린샷을 비교하면 카드 내부 여백·리스트 행 간격 등이 실제로는 이번 수정 전까지 한 번도 의도대로 렌더링된 적이 없었다는 것을 확인할 수 있었다. PC 대시보드/전체콘텐츠/공지사항/로그인 페이지 스크린샷으로 회귀가 없음을 확인했다(PC는 인라인 `style` 위주라 영향이 작았음).

## 1. 레이아웃 진단 요약 (기존 코드 vs 정적 Figma 추출자료 비교)

1. **컨테이너 자체는 이미 반응형이다.** `MobileShell.tsx`의 `lg:w-[440px] lg:h-[900px]`는 데스크톱 프리뷰(≥1024px)에서만 적용되는 "폰 목업 프레임"이며, 실제 모바일 뷰포트(`<lg`)에서는 `w-full h-full`로 정상 동작한다. "고정 규격이라 깨진다"는 가설은 컨테이너 레벨에서는 사실이 아니었다.
2. **진짜 원인들**:
   - `globals.css:31` `html { font-size: 17px }` 전역 오버라이드 — 모든 `rem` 기반 Tailwind 값이 Figma 스펙 대비 약 6% 커짐.
   - `MobileDashboard.tsx:219`, `MobileFullList.tsx:179`의 플로팅 액션 버튼이 `absolute bottom-18`로 **스크롤 컨테이너 기준 절대 위치** — 화면에 고정되지 않고 콘텐츠와 함께 스크롤됨. Figma는 이 버튼들을 항상 하단 고정으로 의도. **체감 "뒤죽박죽"의 핵심 원인 후보 1순위.**
   - `MobileCalendar.tsx:201` `min-h-[72px]` 셀 고정 높이 — 좁은 실기기 폭(iPhone SE 375px÷7열≈50px)에서 아바타+뱃지 오버플로우 위험.
   - `MobileFullList.tsx:54` `min-h-[680px]` 루트 컨테이너 — 실제 콘텐츠/뷰포트 높이와 무관, 짧은/긴 화면에서 여백 어긋남.

## 4. 반응형 구현 원칙 (모든 컴포넌트 공통 적용)

Figma 목업은 402×874(iPhone 14/15급) 1개 폭만 존재하고 §2.1에서 확인했듯 Auto Layout도 대부분 `FIXED`다. 따라서 "Figma와 일치"를 "402px 그대로 하드코딩"으로 오해하면 P0에서 지적한 문제(고정 규격→다른 폭에서 깨짐)가 반복된다. 아래 원칙을 P0~P2 모든 구현에 공통 적용한다.

1. **기준 폭은 402px, 지원 범위는 ~360px(작은 안드로이드)부터 ~430px(iPhone Pro Max)까지.** 402px에서 Figma와 픽셀 단위로 일치시키되, 그 값을 다른 폭에서 그대로 스케일되도록 상대 단위로 변환한다.
2. **고정 px 대신 상대 단위 우선**: 컨테이너 폭은 `w-full`/`max-w-*`, 내부 여백·폰트는 `rem`(전역 `16px` 기준 통일, §3 P0 참고), 아이콘/아바타 등 "고정이어야 자연스러운" 요소만 예외적으로 `px` 허용.
3. **높이는 콘텐츠 기반이 원칙, Figma가 명시적으로 `HUG`인 요소(대시보드 메인위젯 등, §2.1)는 반드시 auto-height로 구현.** `min-h-[72px]`, `min-h-[680px]` 같은 임의 고정값(§1 진단)은 전부 제거하고 `aspect-*`, `flex-1`, 콘텐츠 기반 높이로 대체.
4. **뷰포트 단위는 `dvh`/`svh`만 사용**(`100vh`/`min-h-screen` 금지 — 모바일 브라우저 주소창 문제, §1 참고).
5. **고정 배치 요소(하단 탭바, 플로팅 액션 버튼, 모달 풋터)는 전부 `env(safe-area-inset-bottom)` 반영 + 셸 루트 기준 `fixed`**로 통일(스크롤 컨테이너 기준 `absolute` 금지, §1의 핵심 버그 재발 방지).
6. **그리드(캘린더 7열 등)는 폭에 비례해 셀 크기가 줄어들되 내부 콘텐츠(아바타·뱃지)는 `overflow-hidden`+축소 가능한 크기로 설계**하여 360px에서도 잘리지 않게 한다.
7. bottom navbar, 대시보드 메인위젯처럼 Figma가 이미 가변으로 설계한 요소(§2.1)는 Tailwind `flex-1`/`grow` 등으로 그 의도를 그대로 반영한다.

## 5. 시각적 정합성 검증 워크플로우 (디자인 토큰 추출 + Diff 비교)

레이아웃/인터랙션 구현이 끝난 화면마다 아래 루프로 Figma와의 시각적 일치율을 정량 검증한다. 목표: 기준 폭(402px)에서 diff 3% 이내.

**현재 환경의 제약(진행 전 확인)**
- 이 세션은 `get_design_context`/`get_screenshot` 같은 Figma Dev Mode MCP 도구가 없어 Figma REST API(`X-Figma-Token` 헤더)로 대체했다. 동일 방식을 쓰려면 Personal Access Token을 다시 발급받아야 한다(세션 스크래치패드 저장분은 세션 종료 시 소실, §6 참고).
- `playwright`, `pixelmatch`, `pngjs`는 `package.json`에 없음 — 실행 전 `npm install -D playwright pixelmatch pngjs` 필요(설치는 실제 코드 수정 작업이므로 별도 승인 후 진행).
- **Figma 레퍼런스 이미지는 402px 화면에만 존재한다.** 다른 폭(360/375/390/430px)에는 비교할 원본 이미지 자체가 없으므로, 그 폭들은 diff % 대신 §4 원칙 기반의 체크리스트(오버플로우 없음, 고정요소 안전영역 확보, 비율 유지)로 육안+DevTools 검증한다.

**단계 1 — 디자인 토큰 추출**
1. 대상 노드(§2.2/§2.3의 node id)를 Figma REST API `GET /v1/files/{key}/nodes?ids={NODE_ID}`로 조회해 색상(hex), spacing(px), 타이포(font-family/size/weight/line-height), 컴포넌트 variant, 에셋 목록을 추출.
2. `docs/figma-tokens/{screen-name}.json`으로 저장.
3. 저장 후 추출 토큰 요약을 표로 제시하고, 값이 불명확한 항목은 진행 전에 확인 요청(임의 추정 금지).

**단계 2 — 기준 이미지 확보**
- Figma REST API `GET /v1/images/{key}?ids={NODE_ID}&format=png&scale=2`로 402px 프레임을 PNG export → `docs/figma-tokens/{screen-name}.reference.png` 저장.

**단계 3 — 구현**
- 단계 1의 토큰 값만 사용(임의로 색상/간격/폰트 추정 금지, 값이 없으면 질문). §4 반응형 원칙을 동시에 적용.
- 구현 후 Playwright로 402px 뷰포트 스크린샷 캡처 → `docs/figma-tokens/{screen-name}.actual.png`.

**단계 4 — Diff 검증**
1. `pixelmatch`로 `reference.png` vs `actual.png` 비교.
2. diff 비율(%)과 `docs/figma-tokens/{screen-name}.diff.png` 생성.
3. 보고 형식: `diff율: NN% / 목표: 3% 이내 / PASS or FAIL / FAIL 시 주요 diff 영역(좌표·컴포넌트명)`.

**단계 5 — 반복 및 반응형 스팟체크**
- FAIL이면 diff 영역만 수정 후 단계 3~4 반복.
- 402px PASS 후, 360/375/390/430px에서 §4 체크리스트 기준으로 반응형 스팟체크(스크린샷은 남기되 diff 비교는 하지 않음 — 레퍼런스 부재).
- 최종적으로 화면별 `{screen}.json/reference.png/actual.png/diff.png` + diff율 + 반응형 스팟체크 결과를 함께 기록.

### 5.1 실행 결과 (이번 세션)

전체 17개 화면 대신, 이번 세션에서 Figma 토큰을 정밀 추출해 구현한 3개 정적 요소(동적 DB 콘텐츠가 섞이지 않아 공정한 픽셀 비교가 가능한 요소)에 대해 실제로 워크플로우를 실행했다. 결과물은 `docs/figma-tokens/`에 저장.

| 요소 | node id | diff율 | 목표(3%) | 원인 |
|---|---|---|---|---|
| D-day 기획안 카드 | `863:151012` | 16.22% | FAIL | 라벨/서브타이틀/배경색/radius는 diff.png상 거의 일치. diff는 거의 전부 `D-2`(Figma 목업 값) vs `미설정`(우리 구현, PC 대시보드와 동일한 정직한 폴백) 텍스트 영역에 집중 — **의도된 콘텐츠 차이**, 스타일 결함 아님 |
| D-day 완성본 카드 | `863:151013` | 13.87% | FAIL | 위와 동일 원인(`D-17` vs `미설정`) |
| bottom navbar 글래스 캡슐 | `I863:146818;849:81054` | 42.12%(보정 후) / 79.23%(보정 전) | FAIL | **측정 방법 자체의 한계** — 아래 참고 |

**navbar 측정에 대한 중요한 정정**: Figma REST API로 정밀 추출하는 과정에서 이전 세션의 분석이 틀렸다는 것을 발견했다. `852:34431`(bottom navbar 컴포넌트)을 다시 뜯어보니, "navbar" 캡슐(287×58) 자체에 **이미 4개 탭(대시보드/캘린더/전체 리스트/프로필)이 전부 들어있고**, "cta"(58×58 원형 버튼)는 그 옆에 별도로 붙는 **5번째 요소**였다 — §2.1/§3에 "탭 3개 + 우측 FAB"라고 적었던 것은 틀린 해석이었다(당시엔 이 정도로 세밀하게 뜯어보지 못했음). 즉 Figma는 애초에 "4탭 + 별도 FAB"였지, "프로필 탭을 FAB로 대체"가 아니었다. 사용자가 앞서 "4탭 유지, FAB 미구현"으로 확정한 결정 자체는 여전히 유효한 선택이지만, 그 전제("4탭 유지 시 FAB는 프로필과 양자택일 관계") 가 부정확했다는 점은 밝혀둔다 — **FAB를 추가로 구현할지는 이 사실을 알고 난 뒤 다시 판단할 문제**(이번 세션에서는 구현하지 않음).
이 부정확한 전제와 별개로, 42%라는 수치도 그대로 신뢰하기는 어렵다: 우리 구현은 4탭이 균등폭으로 늘어나 실제 370px로 렌더링되는데, pixelmatch는 두 이미지의 크기가 같아야 해서 이걸 Figma의 287px 폭에 강제로 리사이즈해 비교했고, 그 과정에서 "대시보드" 탭 라벨이 부자연스럽게 눌렸다(개발 서버 전용 Next.js 빌드 인디케이터가 캡처에 겹친 것도 노이즈로 섞임). diff.png를 육안으로 보면 다크 필 활성탭·아이콘·글래스 톤 자체는 상당히 유사하고, 수치가 큰 것은 폭 차이에서 오는 리사이즈 왜곡이 크다.

**결론**: 정량 diff 워크플로우 자체(토큰 추출→레퍼런스 export→구현→pixelmatch→diff.png)는 정상적으로 동작함을 확인했고, 3개 요소 모두 FAIL이지만 원인은 전부 "의도된 설계/콘텐츠 차이"로 설명 가능하며 실제 스타일 결함은 diff.png상 발견되지 않았다. 17개 화면 전체에 이 워크플로우를 반복 실행하려면(특히 동적 DB 콘텐츠가 섞이는 화면은 콘텐츠를 Figma 목업 텍스트로 임시 하드코딩하거나, 콘텐츠 영역을 마스킹하고 레이아웃/스타일 영역만 비교하는 방식이 필요) 추가 세션이 필요하다.

**루프 인프라**: 재사용 가능한 스크린샷+pixelmatch 스크립트를 세션 스크래치패드에 작성해 5개 요소를 일괄 처리했다(개별 요소마다 수작업 반복 없이 설정 배열만 바꾸면 재실행 가능). 17개 화면 전체 커버리지는 여전히 후속 세션 몫이다.

## 8. §5 이후 실사용 피드백 반영 (라이브 Chrome 실기기 투어 중 접수)

§5 diff 검증 + 실기기 에뮬레이션 투어(Playwright로 실제 보이는 Chrome 창을 띄워 로그인부터 전 화면을 실시간으로 시연)를 진행하던 중, 사용자가 실제로 화면을 보면서 5가지 구체적 피드백을 줬다. 전부 이번 세션에 반영 완료.

1. **갤럭시/안드로이드 호환성**: 상단 헤더·모달 헤더에 `env(safe-area-inset-top)`이 전혀 적용되어 있지 않아 펀치홀 카메라 기종에서 헤더가 카메라와 겹칠 수 있었음 → `.safe-pt` 적용(`MobileShell`/`MobileDetailModal`/`MobileSubmitModal` 헤더). `backdrop-filter` 미지원 브라우저(구형 Samsung Internet 등) 대비 `@supports not (backdrop-filter)` 폴백 추가.
2. **하단 탭바 글래스 디자인**: 기존 근사치(단순 blur+반투명 흰색)를 Figma REST API로 재조회한 **정확한 이펙트 스택**으로 교체 — fill은 흰색 5% 불투명도(칼라 알파가 아니라 페인트 레벨 opacity, 처음엔 놓쳤던 값), `backdrop-filter: blur(10px)`, 앰비언트 drop-shadow 2겹(blur 72px/30px) + 내부 하이라이트 4겹. 활성 탭은 불투명 다크 네이비가 아니라 **검정 40% 반투명**(smoked-glass) 필이었음 — `globals.css`의 `.glass-navbar`/`.glass-navbar-active`로 구현.
3. **기획안/완성본 상세보기 콘텐츠 불완전**: 조사 결과 두 종류의 문제가 겹쳐 있었다.
   - **데이터 버그**: 완성본 뷰가 기획안 전용 필드(`intent`/`keywords`)를 그대로 재사용해 완성본에 기획안 내용이 잘못 표시되고 있었음 → PC(`ContentsLayout.tsx`)와 동일하게 `postContent`/`finalDescription`/`finalKeywords`로 분리.
   - **누락 필드**: `구성 및 내용`(`bodyObj.composition`), `촬영 계획`(`bodyObj.contentBody`), `데드라인`(`bodyObj.deadline`), 읽기 전용 피드백/댓글 스레드(`bodyObj.discussions`)가 통째로 빠져 있었음 → 전부 추가. 기존 `description` 필드는 PC 라벨("비고")과 다르게 "구성 및 내용 설명"으로 오표기돼 있던 것도 수정.
   - **서식 손실**: 리치텍스트(이미지·줄바꿈 포함)를 `stripHtml()`로 평문화하고 있었음 → PC와 동일하게 `dangerouslySetInnerHTML` + `.rich-text-content`로 렌더링(내부 사용자 전용 콘텐츠라 PC와 동일한 신뢰 모델 적용, 새로운 취약점 아님).
   - **레이아웃 근본 버그(피드백 조사 중 발견)**: 상세보기가 콘텐츠가 길어질 때 화면 밖으로 밀려 보이는(스크롤이 아니라 통째로 위치가 어긋나는) 버그를 발견 — 원인은 `MobileShell`의 높이 체인이 전부 `min-h-*`(최소값)로만 구성돼 있어 `absolute inset-0`로 붙인 모달이 기댈 "확정된 높이"가 없었기 때문. `min-h-dvh` → `h-dvh`(확정값)로 교체하고 데스크톱 프리뷰 대비 `lg:overflow-y-auto` 안전장치 추가로 해결.
4. **전체 리스트 분기별(2개월 단위) 필터**: Figma의 "월 선택 드롭다운" 컴포넌트가 3-variant(3,4월/5,6월/7,8월)만 있어 §2.3에서 "미사용/보류"로 판단했었으나, 사용자가 전체 리스트 화면의 달력 아이콘과 연결되는 기능이라고 확인해줌 → 전체 6구간(1,2월~11,12월)으로 확장해 `MobileFullList` 검색바 옆에 달력 아이콘 + 드롭다운으로 구현, `target_date` 월 기준 필터링.
5. **리스트 선택→미리보기→상세보기 진입 메커니즘 + 종이 슬라이드 모션**: 전체 리스트 하단의 "기획안 작성/완성본 업로드" 고정 버튼을, 리스트에서 선택한 콘텐츠의 실제 기획안/완성본 축소 미리보기로 교체(선택 상태는 `MobileShell`으로 끌어올려 셸 고정 레이어에서 렌더링). 완성본이 없으면 잠금 처리하되, 본인이 작성한 콘텐츠면 완성본 업로드로 연결. 상세보기 진입/종료 모션을 `fade-in`+X버튼 닫기에서 `slide-in-from-bottom`(종이를 아래에서 꺼내는 모션) + 드래그 핸들로 아래로 스와이프하면 닫히는 제스처로 교체 — `useSwipeDownToDismiss` 훅으로 `MobileDetailModal`/`MobileSubmitModal` 양쪽에 공용 적용했기 때문에 대시보드의 기획안 작성/완성본 업로드 진입도 자동으로 동일한 모션을 갖게 됐다(별도 작업 불필요).

이 라운드의 코드 변경 후에도 `npm run build` 통과 확인, 실시간 Chrome 창으로 전체 플로우(글래스 navbar, 리스트 선택→미리보기→상세보기 슬라이드업→스와이프다운 닫기, 분기 필터, 완성본 잠금 상태) 재확인 완료.

## 9. §8 이후 정합성/모션 추가 요청 (2차 라운드)

§8 반영 후 사용자가 두 가지를 더 요청했다: (1) 전체 리스트 하단이 "기획안 보기/완성본 보기" 텍스트 버튼이 아니라 Figma처럼 **문서 그림 형태**여야 한다, (2) 전반적 모션이 부족하다.

**Figma 재조사로 발견한 사실**: 전체 리스트 메인 화면(`863:17013`)의 자식 노드를 다시 뜯어보니, 화면 하단에 "기획안"(`863:80116`, 192.8×484.5)과 "완성본"(`863:141799`, 192.8×446.5) 두 INSTANCE가 실제로 존재했고 — 이전에는 이 두 노드를 조사하지 않았다 — 이들은 **실제 기획안/완성본 작성 폼 전체를 그대로 담고 있는 미니어처**였다(제목/콘텐츠분류/참여인원/기획의도/구성및내용/촬영계획/해시태그/업로드시기/데드라인/비고 필드가 전부 들어있음, 실제 폼 대비 약 46% 스케일). 두 컴포넌트는 메인 화면 프레임 밖(y=463~947.5, 프레임은 -272~602)에 파킹돼 있어 정적 목업에서는 보이지 않고, 선택 시 애니메이션으로 등장하는 "peek 소스" 역할로 설계된 것으로 보인다.

**구현**:
- `MobilePaperPreview.tsx` 신규 컴포넌트: 실제 크기로 마크업을 그린 뒤 `transform: scale(0.56)`로 시각적으로 축소해 "종이 문서" 느낌을 재현(타이핑된 값 몇 개짜리 텍스트 버튼이 아니라 실 데이터 기반 필드 박스 스택). 기획안/완성본 각각 실데이터(제목/분류/크루/기획의도/구성/촬영계획/해시태그/날짜/비고, 완성본은 postContent/finalDescription/finalKeywords)로 채움. 완성본이 없으면 잠금 오버레이(그레이스케일+🔒), 본인 콘텐츠면 업로드 유도 오버레이(📤 점선 테두리)로 상태를 표시.
- **FLIP 공유 요소 전환**: 카드를 탭하면 `getBoundingClientRect()`로 그 카드의 화면 좌표를 캡처해 `MobileDetailModal`에 `originRect`로 전달 → 모달이 그 좌표/크기에서 시작하는 `translate()+scale()`을 인라인 스타일로 먼저 적용한 뒤(무전환) 다음 프레임에 identity로 되돌려(CSS transition 적용) "카드가 화면 전체로 커지는" 모션을 재생. 닫을 때(X/닫기 버튼/스와이프 드래그 임계값 초과)는 역순으로 같은 좌표까지 줄어든 뒤 실제로 언마운트. `originRect`가 없는 경로(대시보드 미리보기 드로어, 캘린더 팝업 등 카드가 없는 곳에서 여는 경우)는 기존 `slide-in-from-bottom` 폴백을 그대로 사용.
- 리스트에서 선택 항목이 바뀔 때 미리보기 패널에 `key`+`fade-in`을 적용해 콘텐츠 전환에도 모션 부여.

`npm run build` 통과, headless Playwright로 FLIP 애니메이션 중간 프레임(60ms/160ms) 캡처해 카드 위치→전체화면으로 정상 보간되는 것을 확인, 실시간 Chrome 창으로 최종 확인 완료.

## 10. §9 이후 peek 위치/대시보드 구조 재요청 (3차 라운드)

§9 반영 후 사용자가 두 가지를 추가로 지적했다: (1) 전체 리스트의 미니어처 패널이 여전히 화면 중간 근처에 떠 있어 너무 높다, Figma에서 같은 레이어를 직접 스크린샷 비교해서 정확한 비율로 맞춰달라, (2) 메인 대시보드의 "기획안 미리보기"는 원래 상세보기 UI 그 자체이며, 탭하거나 위로 스와이프하면 전체화면 상세보기로 펼쳐지는 구조였다 — 지금의 단순 드로어(제목/팀/버튼 텍스트만 있는 커스텀 바텀시트)가 아니라 그 구조와 모션을 그대로 구현해달라.

**Figma 재조사로 발견한 사실**: 전체 리스트의 "기획안"/"완성본" 미니어처(§9, `863:80116`/`863:141799`)와 대시보드 화면에 있는 peek 상태의 기획안/완성본 인스턴스가 **`componentId`(기획안 `856:37923`, 완성본 `856:37924`)까지 완전히 동일한 마스터 컴포넌트**라는 것을 REST API로 확인했다. 즉 이 컴포넌트는 세 곳에서 서로 다른 크기/위치의 인스턴스로만 쓰인다:
1. 전체 리스트의 "파킹된" 원본 인스턴스(§9, 화면 밖에 대기)
2. 대시보드의 **peek 인스턴스** — 부모 프레임(874px 높이) 기준 `y=605px`, 즉 상단에서 **69.2%(605/874)** 지점부터 시작해 화면 하단까지 차지
3. (프로토타입에는 없지만) 탭/스와이프 시 도달하는 **full 인스턴스** — `y≈0`, 화면 전체

이 componentId 일치는 두 가지를 동시에 확정해준다: 전체 리스트 미니카드 패널이 시작해야 할 정확한 위치(화면 상단 기준 69.2%)와, 대시보드 미리보기가 "상세보기 UI 그대로"여야 한다는 사용자 설명이 문자 그대로 맞다는 것(같은 컴포넌트이므로 다른 마크업일 수가 없음). 다만 이 peek↔full 전환 자체를 잇는 프로토타입 reaction은 Figma에 없어(§2에서 이미 확인) 모션은 직접 설계해야 했다.

**구현**:
- **전체 리스트 미니카드 패널 위치 수정**(`MobileShell.tsx`): 컨테이너를 `top-[69.2%] bottom-0`으로 고정해 Figma의 peek 인스턴스와 동일한 지점에서 시작하도록 수정(기존에는 화면 중앙 부근에 대략 배치돼 있었음). **[§11에서 정정: 이 69.2%는 대시보드 peek 인스턴스의 값이었고, 전체 리스트 화면 자체는 별도의 더 낮은 비율(83.5%)을 쓴다 — §11 참고.]**
- **대시보드 peek→full 재구축**(`MobileDetailModal.tsx`에 `startPeek` prop 추가): 기존에 `MobileDashboard.tsx` 안에 있던 별도의 단순 드로어(제목/팀/"상세 페이지 보기" 버튼만 있는 커스텀 바텀시트, `activeTabDrawer`/`selectedDrawerItem` 로컬 상태)를 완전히 제거하고, 승인대기 항목 탭·프리뷰 캐러셀 탭이 전부 `MobileShell`의 새 `handleOpenPeek(item, type)`을 호출하도록 변경. 이 핸들러는 `MobileDetailModal`을 `startPeek=true`로 열어, **동일한 상세보기 컴포넌트**를 `translateY(69.2dvh)`로 밀어낸 상태(= peek)로 렌더링한다:
  - `viewState: 'peek' | 'full'` 상태를 modal에 추가. peek 상태에서는 뒤에 반투명 딤 배경(탭하면 닫힘)이 깔리고, 패널 자체를 탭하거나 핸들을 위로 스와이프(`dy < -30`)하면 `viewState`가 `full`로 바뀌어 `translateY(0)`(전체화면)까지 부드럽게 확장된다.
  - 기존 FLIP(카드 위치에서 시작, `originRect` 기반)과는 별개 경로로 분리: `startPeek`가 true면 FLIP의 좌표 계산을 건너뛰고 peek 전용 transform을 쓴다. 두 진입 모드(전체 리스트 카드 탭 = FLIP, 대시보드 미리보기 탭 = peek)가 서로 간섭하지 않음을 확인.
  - 닫기 모션도 대칭으로 맞춤: peek로 연 모달은 X 버튼/딤 배경 탭/아래로 스와이프 중 무엇으로 닫든 `translateY(100dvh)`까지 화면 아래로 완전히 슬라이드아웃된 뒤 언마운트("종이가 다시 내려가는" 모션) — 기존에는 이 경로가 애니메이션 없이 즉시 사라졌음.
  - 탭전환("완성본 뷰" 토글)·닫기 버튼들에 `e.stopPropagation()`을 추가해 peek 상태에서 그 버튼들을 눌렀을 때 패널 전체의 "탭하면 확장" 핸들러가 같이 발동하지 않도록 분리.

Playwright로 402×874 뷰포트에서 전 구간 확인: peek 패널 바운딩박스 `y=604.8px`(정확히 69.2%) + 딤 배경 렌더 확인 → 패널 탭 시 전체화면(실제 상세보기 콘텐츠: 제목/콘텐츠분류/참여인원/기획의도 등)으로 정상 확장 → X 버튼(peek 상태에서 직접 닫기, full 상태에서 닫기 둘 다)/딤 배경 탭 각각 콘솔 에러 없이 정상 언마운트 확인. 전체 리스트 미니카드 패널도 같은 세션에서 재확인해 회귀 없음을 확인. `npm run build` 통과.

## 11. §10 이후 전체 리스트 도크 구조/필터 노출 방식 재요청 (4차 라운드)

§10 반영 후 사용자가 전체 리스트 화면에 대해 두 가지를 추가 지적했다: (1) 미니카드 두 장이 여전히 너무 높고, `MobileShell`이 절대좌표 오버레이로 얹어놓은 방식이라 "리스트와 한 레이어에서 같이 스크롤되는 느낌"이 난다 — Figma처럼 리스트 구역 **아래**에 겹치지 않고 고정으로 나란히 있어야 하며, 차지하는 비중을 지금의 2/3 수준으로 줄여 더 아래로 내려가야 한다. (2) 검색바/달력 버튼/소속·유형 필터를 기본적으로 숨기고, 상단 GNB의 돋보기 아이콘을 눌렀을 때만 전체 리스트 화면으로 이동하면서 그 필터 영역이 드러나고 검색창에 포커스+키보드가 뜨도록 바꿔달라.

**Figma 재조사로 발견한 사실**: §10에서는 전체 리스트의 미니카드 위치를 대시보드 peek 인스턴스의 비율(69.2%)로 그대로 재사용했는데, 이번에 전체 리스트 화면(`863:17013`) 자체를 REST API로 다시 조사해보니 **그 화면 고유의 다른 레이아웃**이 있었다: "리스트 공간" 프레임이 화면 상단 기준 `y=110`에서 시작해 `y=730`에서 끝난다(874 기준 **83.5%**). 기획안/완성본 인스턴스는 바로 그 아래 `y=735`(84.1%)부터 시작하고, 탭 히트 영역("Transparent (기획안/완성본)" 사각형)은 `y=735`부터 높이 58px — 즉 리스트 구역이 끝나는 지점 바로 아래, 아주 얇은 슬리버(peek 힌트)만 화면에 걸쳐 있고 카드의 나머지는 프레임 밖에 파킹되어 있는 구조다. 대시보드 peek(69.2%)와 전체 리스트 도크(83.5%)는 같은 마스터 컴포넌트를 쓰지만 화면마다 다른 위치에 배치된, 서로 다른 인스턴스였다.

**구현**:
- **도크를 오버레이 → 실제 flex 형제로 재구조**(`MobileShell.tsx`): 기존에는 `<main>`(스크롤되는 리스트) 위에 `position: absolute`로 얹혀 있어서, 실제로는 겹쳐 있을 뿐 리스트 자체의 높이는 줄지 않았다(리스트를 스크롤하면 도크 뒤로 콘텐츠가 지나가는 형태). 이제 도크를 `<main>`의 일반 flex 형제(`flex-shrink-0 h-[9rem]`, absolute 아님)로 옮기고 `<main>`에 `min-h-0`을 추가해, `<main>`이 `flex-1`로 실제로 도크 높이만큼 줄어들도록 했다 — 리스트와 도크가 레이아웃상 완전히 분리된 별도 영역이 되어, 리스트를 아무리 스크롤해도 도크는 같은 자리에 그대로 있다(겹쳐서 같이 스크롤되는 느낌 해소).
- **비율 수정**: `top-[69.2%]` 하드코딩을 버리고, 리스트 공간이 끝나는 지점(730/874=83.5%)에 맞춰 도크 높이를 `9rem`(Figma의 남은 144px÷16)으로 고정. 기존 대비 화면 점유 비율이 30.8%→16.5%로 줄어 사용자가 요청한 "2/3 수준으로 축소, 더 아래로"라는 방향과 일치한다(정확한 분수보다 Figma 실측값을 우선 적용).
- **검색/필터 숨김·노출 토글**(`MobileFullList.tsx`): `showFilters` 상태(기본 `false`)를 추가해 검색바+분기 달력 버튼+소속/유형 필터 두 줄을 `max-height` 트랜지션으로 접어둔다. 조건부 마운트(`{cond && <input/>}`) 대신 **입력 필드를 항상 DOM에 유지한 채 `max-h-0`로만 시각적으로 접는 방식**을 택했다 — 조건부 마운트라면 펼친 직후 방금 마운트된 input에 focus를 걸어야 해서 한 프레임 지연이 생기고, 실기기(특히 iOS Safari)에서는 그 지연 때문에 키보드가 안 뜰 수 있다. 필터가 펼쳐지면 검색바 옆에 "취소" 버튼이 나타나 다시 접을 수 있다.
- **GNB 연동**(`MobileShell.tsx`): 상단 🔍 버튼이 기존에 띄우던, 실제로는 어떤 필터링에도 연결돼 있지 않던 장식용 검색 오버레이(`isSearchOpen`/`searchQuery`)를 완전히 제거하고, 탭마다 증가하는 카운터(`listSearchTrigger`)를 `MobileFullList`에 `revealSearch` prop으로 내려주도록 교체. 탭 한 번으로 `activeTab`을 `'list'`로 전환 + 카운터 증가가 동시에 일어나고, `MobileFullList`는 그 값이 바뀔 때마다(0에서 시작 → 처음 진입 시엔 아무 동작 안 함) `showFilters(true)` + `searchInputRef.current?.focus()`를 실행한다. 카운터 방식을 쓴 이유는 이미 전체 리스트 탭에 있고 필터도 이미 펼쳐진 상태에서 GNB 돋보기를 또 눌러도(값이 다시 바뀌므로) 재포커스가 걸리게 하기 위함이다.

Playwright로 402×874 뷰포트에서 확인: 도크 바운딩박스 `y=730px`(정확히 83.5%) 확인, 리스트를 스크롤(`scrollTop=300`)해도 도크 위치가 그대로임을 재확인(오버레이가 아닌 진짜 분리 레이아웃임을 증명) → 대시보드에서 GNB 🔍 탭 시 전체 리스트로 전환되고(`nav`의 활성 탭 라벨로 확인) 필터 섹션이 펼쳐지며 검색 input이 `document.activeElement`가 됨을 확인(실기기 키보드 트리거의 가장 신뢰할 수 있는 대리 지표) → 실제로 텍스트를 입력해 필터링까지 정상 동작 확인(예: "테스트" 입력 → 총 1개로 축소) → "취소"로 재접힘 확인. 콘솔 에러 없음. `npm run build` 통과.

## 12. §11 이후 소소한 수정 + 글래스 CTA + 캘린더 peek→full (5차 라운드)

이번 라운드는 작은 수정 두 건과, 세션 초반부터 범위 밖으로 미뤄뒀던 큰 항목 두 건(캘린더 peek→full, 대시보드 CTA 글래스화)을 사용자가 직접 우선순위를 골라 진행했다.

**소소한 수정 2건**:
- `MobileCalendar.tsx`: 날짜팝업 콘텐츠 카드에서 불필요한 "전체 상세보기 ➔" 문구 제거(카드 자체가 이미 탭하면 상세보기로 연결됨 — 텍스트가 오히려 카드 밖에 별도 링크가 있는 것처럼 오해를 줌).
- `MobileFullList.tsx`: GNB 돋보기를 다시 누르면 이미 펼쳐진 필터가 다시 접히도록 진짜 토글로 전환. 구현 중 `setShowFilters(prev => { ...; if (next) focus(); ...})`처럼 **상태 업데이터 함수 안에서 DOM 부수효과(focus/blur)를 실행하던 버그**를 발견했다 — React Strict Mode는 업데이터 함수의 순수성을 검증하려고 개발 모드에서 그 함수를 일부러 두 번 호출하는데, 부수효과가 있으면 그 부수효과도 두 번 실행돼 의도치 않은 동작이 생길 수 있다. focus/blur를 업데이터 밖, `showFilters` 값에 반응하는 별도 `useEffect`로 분리해 해결했다.

**대시보드 CTA 4개 글래스 디자인**: Figma REST API로 두 버튼 쌍을 직접 조사했다 — 상단 고정 "기획안 작성"/"완성본 업로드"(componentId `960:16326`/`960:16347`)는 단색 채우기(`#99B3D6`/`#003378`)만 정의돼 있고 블러 효과가 없었고, 캐러셀의 "기획안 보기"/"완성본 보기"는 Figma 어디에도 없는, 이전 세션에서 새로 만들어 넣은 버튼이었다(카드더미 안에 있는 것은 북마크/댓글수 아이콘 버튼일 뿐, 텍스트 CTA가 아니었음). 즉 "글래스로 바꿔달라"는 요청 자체가 Figma 재현이 아니라 **새로운 디자인 결정**이라는 것을 사용자에게 알리고, 두 버튼 쌍 모두("둘 다") 바꾸는 것으로 확인받았다. `globals.css`에 `.glass-cta`(연한 반투명 화이트, 보조 버튼용)/`.glass-cta-primary`(반투명 네이비, 주요 버튼용)를 navbar와 같은 `blur(10px)` 재질·쉐도우 레이어링 관례로 신규 작성해 네 버튼 모두에 적용, 앱 전체의 글래스 비주얼 언어를 일관되게 확장했다.

**캘린더 peek→full(캘린더4/5/6/7)**: 세션 초반 조사에서 이미 기록해뒀던 캘린더 인터랙션 그래프(§2.2)를 다시 확인하고, 거기 적혀 있던 "패널 top=318px / 142px" 수치를 이번에 **다시 Figma REST API로 직접 재검증**했다(전체 리스트 도크 때 69.2%를 잘못 재사용했던 실수를 반복하지 않기 위해). 결과:
- **캘린더4/5(peek)**: `기획안`/`완성본` 인스턴스가 화면(874px) 기준 `y=318`에서 시작 — **36.4%**. 대시보드 peek(69.2%)와는 다른, 이 팝업 화면 고유의 비율이다(같은 componentId `856:37923`/`856:37924`를 다른 위치에 배치한 것 — 대시보드/전체리스트와 동일한 패턴).
- **캘린더6/7(full)**: 인스턴스가 `y=0`, 즉 화면에 완전히 플러시 — 이전 기록의 "142px"는 실제로는 배경 탭 히트 영역(`Transparent (Back)`)의 높이였지 패널 시작 위치가 아니었다(문서 오기 정정).
- **닫기 동작**: 세션 초반에 이미 사용자가 확정해뒀던 설계("상세보기 뒤배경/닫기 버튼 탭 → 미리보기로 복귀")를 이번에 실제로 구현했다. `MobileDetailModal`의 `closeAnimated`가 `viewState==='full'`이면 완전히 닫는 대신 `'peek'`로 한 단계만 되돌아가고, `'peek'`에서 다시 닫으면(뒤 배경 탭/아래로 스와이프/X) 그제서야 화면 아래로 슬라이드아웃되며 완전히 사라진다 — 이 규칙은 캘린더뿐 아니라 대시보드 peek→full에도 동일하게 적용된다(같은 컴포넌트를 공유하므로).

**구현**: `MobileDetailModal`의 `PEEK_TOP_VH` 상수를 `peekTopVh` prop(기본값 69.2)으로 바꿔 화면마다 다른 비율을 쓸 수 있게 하고, `MobileShell`의 `handleOpenPeek(item, type, peekTopVh)`가 이 값을 그대로 전달받아 넘긴다. `MobileCalendar`에 새 `onOpenPeek` prop을 추가해 날짜팝업의 카드 탭이 (기존의 즉시 전체화면 `onOpenDetail` 대신) `handleOpenPeek(item, type, 36.4)`를 거치도록 변경(그리드 뷰 옆의 별도 "리스트 보기" 모드는 이번 요청 범위 밖이라 기존 즉시-전체화면 동작 유지).

Playwright로 402×874 뷰포트에서 확인: peek 패널 바운딩박스 `y=318.1px`(정확히 36.4%) → 패널 탭 시 전체화면(`y=0`)으로 확장 → X 버튼 1차 탭: peek로 복귀(`y=318.1px`, 완전히 닫히지 않음) 확인 → X 버튼 2차 탭: 완전히 닫힘 확인. 콘솔 에러 없음. `npm run build` 통과.

## 13. §12 이후 전체 리스트 미니카드/뱃지 폴리시 (6차 라운드)

빠른 실시간 반복 라운드. 사용자가 실시간 미리보기(핫리로드)로 직접 보면서 방향을 잡았다.

- `MobilePaperPreview.tsx`: 미니카드 2개의 배경/테두리/그림자를 모두 제거해 완전 투명화(글래스도 고려했다가, 62% 불투명 글래스로 한 번 적용해봤지만 사용자가 최종적으로 완전 투명을 선택). `globals.css`의 `.glass-card`는 미사용이 되어 삭제.
- `MobileShell.tsx`: 미니카드를 담는 도크 컨테이너를 §11에서 `<main>`과 겹치지 않는 flex 형제로 바꿨었는데, 이번에 다시 `position:absolute`(리스트 위에 겹치는 오버레이)로 되돌렸다 — 도크/카드가 완전 투명해지면서 사용자가 "뒤에 가려진 리스트 항목이 비쳐 보여야 한다"고 요청했고, 겹치지 않는 구조에서는 애초에 겹친 콘텐츠가 없어 투명도가 의미가 없었기 때문(사용자에게 이 트레이드오프를 명시적으로 설명하고 확인받음 — §11의 "안 겹치게" 결정을 되돌리는 것임을 알고 진행). `<main>`에도 다시 도크 높이만큼 하단 padding을 둬서 마지막 리스트 항목이 오버레이 뒤에 가려지지 않게(클릭 타겟 겹침 방지) 했다.
- `MobileFullList.tsx`: 리스트 항목 우측의 "기획안"/"완성본" 텍스트 뱃지를 완전히 제거. 항목이 존재하는 것 자체가 기획안의 존재를 의미하므로 불필요한 중복 정보였다는 사용자 판단. 완성본 여부는 Google Drive 링크가 있을 때만 뜨는 아이콘(기존 로직 그대로)만으로 충분히 구분되도록 함.

Playwright로 확인: 뱃지 텍스트 0개(전 항목), 리스트를 끝까지 스크롤한 상태에서도 도크 영역 너머로 스크롤된 리스트 항목/로딩 스피너가 실제로 비쳐 보임(겹침 구조 정상 작동) 확인. 콘솔 에러 없음. `npm run build` 통과.

## 14. §13 이후 빠른 폴리시 라운드 (7차 라운드)

도크 글래스 패널(§12 마지막)에 이어, 사용자가 실시간 미리보기를 보며 마이너 수정 여러 건을 연달아 요청. 각각 독립 커밋으로 반영.

- **도크 패널 유지, 미니카드는 원래 스타일로**: "도크는 글래스, 미니카드는 원래대로"라는 사용자 지시에 따라 `MobilePaperPreview`의 카드 배경을 다시 불투명 `#FAFAFA` + 테두리/그림자로 복원(§13에서 완전 투명으로 만들었던 것을 재조정). 도크(`.glass-dock`) 위에 또렷한 종이 카드가 얹힌 모양으로 정착.
- **도크 내부 스크롤 제거**: 미니카드 2개가 내부 스크롤될 필요가 없다는 지적에 따라 `overflow-y-auto` → `overflow-hidden`.
- **Google Drive 아이콘 실물 교체**: 기존 SVG path가 실제 로고와 어긋나 있었다(특히 파란색 조각이 로고 중앙의 작은 삼각형으로 잘못 그려져 있었음 — 실제로는 하단의 큰 평행사변형이어야 함). Wikimedia Commons의 공식 "Google Drive icon (2020).svg"에서 정확한 path 데이터를 가져와 `MobileFullList`/`MobileDetailModal` 두 곳 모두 교체.
- **전체 리스트 선택 토글 + 빈 상태 처리**: 이미 선택된 항목을 다시 탭하면 선택 해제되도록 변경. 선택이 없을 때는 도크 대신 대시보드와 동일한 글래스 CTA 버튼(기획안 작성/완성본 업로드)이 뜨도록 조건 통합. 필터 변경으로 선택이 무효화됐을 때만 정리하고, 사용자가 직접 선택 해제한 상태는 강제로 다시 채우지 않도록 자동선택 useEffect도 함께 정리.
- **상단 GNB 헤더 글래스화**: `.glass-header` 추가, sticky 헤더 뒤로 스크롤 콘텐츠가 블러되어 비치게 함.
- **대시보드 peek 미리보기 좌우 스와이프**: peek 상태에서 미리보기 내용을 좌우로 스와이프하면 기획안⇄완성본 탭이 전환되도록 추가(기존 헤더 버튼과 별개 경로). 스와이프 제스처 뒤에 이어지는 합성 click이 peek→full 확장을 함께 발동시키지 않도록 suppressNextClick 가드 추가.
- **캘린더 월간 그리드 재구성**: 사용자가 공유한 Timeblocks 앱 스크린샷을 참고해, 정사각형 셀 + 최대 2개 축소 뱃지였던 기존 방식을 세로로 넉넉한 셀 + 꽉 찬 너비의 이벤트 막대(최대 3개 + "+N개")로 교체. 날짜 숫자는 좌측 상단 작은 원으로 이동. 콘텐츠 데이터에는 여러 날에 걸친 일정이 없어(각 콘텐츠가 단일 희망 업로드 날짜만 가짐), Timeblocks의 다중일 스팬 바 렌더링은 구현하지 않고 단일 날짜 막대 스택까지만 반영 — 색상은 기존 기획안(주황)/완성본(초록) 의미 체계 유지.

각 항목 Playwright로 개별 검증(스크린샷 + 상태 확인) 후 커밋. 콘솔 에러 없음, `npm run build` 매 라운드 통과.

## 15. §14 이후 GNB 글래스 재요청 → 세션 전체 글래스 블러 미적용 버그 발견

사용자가 "GNB도 글래스로"를 다시 요청 — §12에서 이미 `.glass-header`를 적용했던 것이라 재확인해보니, `getComputedStyle`상 `backdropFilter: "none"`으로 나왔다. 컴파일된 CSS를 직접 다운로드해 뜯어본 결과 원인 확정: Turbopack의 CSS 압축기가 `backdrop-filter`/`-webkit-backdrop-filter`를 같은 속성으로 취급해 병합하면서, 소스에서 표준 속성을 먼저 쓰면 그걸 버리고 접두사 버전만 남긴다 — 현재 크롬은 접두사만으로는 블러를 적용하지 않는다. 즉 **이번 세션에서 만든 모든 글래스 요소(navbar, CTA 버튼, 도크, 헤더)가 실제로는 한 번도 블러 없이 반투명 단색으로만 렌더링되고 있었다.** 스크린샷상 반투명 색만으로도 "그럴듯해" 보여서 여러 차례의 육안 검증에서도 놓쳤다.

수정: `-webkit-backdrop-filter`를 표준 `backdrop-filter`보다 먼저 쓰면 압축기가 표준 속성을 살려둔다는 것을 확인, 전체 `.glass-*` 규칙에 순서를 뒤집어 적용(`globals.css`에 재발 방지 주석 추가). `getComputedStyle().backdropFilter`가 `"none"` → 실제 `"blur(Npx)"` 값으로 바뀌는 것을 코드로 직접 확인 후 스크린샷으로도 재검증 — 헤더/CTA 버튼 뒤로 스크롤 콘텐츠가 눈에 띄게 블러되어 비치는 것을 확인했다.

## 16. §15 이후 GNB 흰색 틴트 제거 + 전체 리스트 도크/상세보기/캘린더 재구성 (8차 라운드)

빠른 실시간 반복이 이어졌다.

- **GNB 헤더**: 사용자가 "흰색 배경 없애면 투과가 더 잘 보일 것"이라며 배경을 완전 투명으로(블러는 유지) 변경 요청 → 반영. 다음 턴에 "롤백"이라 했지만 뒤이은 설명이 정확히 현재 상태(흰 배경 없음+블러 유지)를 가리켜, 실제 되돌릴 코드는 없었고 확인 응답만 함.
- **전체 리스트 도크 → 아이콘 버튼 2개**: 미니어처(축소 렌더링) 시스템 전체를 폐기하고 대시보드 CTA와 동일한 자리·스타일의 아이콘 버튼(📄 기획안 상세보기 / Drive 아이콘 완성본 상세보기, 완성본 없으면 비활성화)으로 교체. `MobilePaperPreview.tsx` 완전 삭제, `.glass-dock` CSS도 함께 제거.
- **캘린더**: Timeblocks 캡처를 다시 참고해, 캘린더 전체를 감싸던 흰색 카드(`bg-white rounded-3xl shadow-sm border`)를 제거 — 셸의 기본 배경 위에 캘린더가 직접 구성되도록.
- **상세보기 헤더/푸터 전면 재구성**: navy 헤더(전환 버튼+작성자+X) 완전 제거. 좌상단에 글래스 상태 배지(기획안 amber/완성본 green, 스크롤 무관 고정) 신규 추가. 작성자/날짜는 제목(가제) 카드 우상단으로 이동(줄바꿈 문제였던 기존 헤더 텍스트 자체가 사라짐). 하단 "닫기" 단일 버튼을 "수정하기"/"닫기" 글래스 버튼 2개로 분할(`.glass-footer` 신규 — `.glass-header`와 재질은 같지만 경계선이 위쪽). "수정하기"는 현재 같은 종류의 빈 작성 폼을 여는 최소 구현 — `MobileSubmitModal`이 기존 데이터 pre-fill을 지원하지 않아 진짜 "수정"은 아직 아님(후속 필요 시 별도 착수).
- **좌우 스와이프 탭전환 확장**: peek 전용이었던 제스처를 full 상태에도 동작하도록 확장.

Playwright로 각 항목 개별 검증(스크린샷 + 상태 확인, full 상태 스와이프로 배지가 기획안→완성본 전환되는 것까지 확인) 후 커밋. 콘솔 에러 없음, `npm run build` 매 라운드 통과.

## 17. §16 이후 GNB 해체, 글래스 톤 조정, 상세보기 마감 다듬기 (9차 라운드)

가장 긴 실시간 반복 라운드. 여러 메시지가 겹쳐서 도착해 순서대로 처리.

- **GNB 헤더 해체**: 하나로 이어진 글래스 바를 로고/타이틀, PC 뷰, 검색, 알림 — 4개의 독립된 `.glass-cta` 조각으로 분리. `<header>` 자체는 배경 없는 투명 컨테이너.
- **GNB 헤더 sticky→absolute 정정**: "분리는 마음에 드는데 여전히 레이어가 남아있다"는 피드백으로 조사한 결과, `<header>`/`<main>`이 스크롤되지 않는 바깥 flex-col의 형제라 `sticky`가 이 구조에서는 실질적으로 무효(붙을 스크롤 컨테이너가 없음)였다는 걸 발견 — header가 그냥 자기 자리를 차지하는 별도 구획이었고 main 콘텐츠가 실제로 뒤를 지나가지 않았다. 바텀 navbar처럼 `absolute`로 바꿔 진짜 오버레이가 되도록 수정, `<main>`에 헤더 높이만큼 상단 패딩 추가.
- **글래스 톤 조정**: 흰색 계열(`.glass-cta`)은 밝은 셸 배경과 구분이 잘 안 된다는 피드백으로 `.glass-cta-strong`(불투명도 0.16→0.4) 보조 클래스를 추가해 기획안 작성/문서 아이콘/수정하기 버튼에 적용. 반대로 navy 계열(`.glass-cta-primary`)은 짙은 색이 낮은 알파에서도 꽤 불투명해 보인다는 이유로 0.55→0.38로 낮춤(방향이 반대인 두 조정).
- **검색창 포커스 링 클리핑**: 접이식 필터 래퍼의 `overflow-hidden`이 인풋 바로 옆이라 포커스 링(box-shadow)의 위/왼쪽이 잘렸다 — 내부 패딩 + 보정 마진으로 여백 확보.
- **전체 리스트 하단 액션 & 캘린더 리스트뷰**: 미니카드 도크를 대체한 아이콘 버튼(§16)과 동일하게, 캘린더의 "리스트로 보기"에서도 기획안/완성본 텍스트 뱃지를 제거하고 완성본은 Drive 링크가 있을 때만 아이콘으로.
- **상세보기 마무리**: 푸터의 도크 배경(`.glass-footer`) 제거해 수정하기/닫기 버튼이 콘텐츠 위에 직접 뜨도록(헤더 해체와 같은 원칙). 좌우 스와이프 탭전환 방향이 실사용 피드백과 반대라 수정. 좌상단 배지를 탭 가능하게 만들어 기획안⇄완성본 전환 기능 추가(완성본 없음+본인 콘텐츠→업로드로, 완성본 없음+타인 콘텐츠→중앙 토스트 "아직 완성본이 업로드 되지 않았습니다"). 하단 액션 버튼 4종의 높이가 텍스트/아이콘 콘텐츠 차이로 미묘하게 안 맞던 것을 `h-14` 고정 높이로 통일. 작성자/날짜 칩을 제목 카드 "안"이 아니라 카드 밖 우상단의 독립 칩으로 이동(배지와 대칭).
- **리치 텍스트 서식 정규화**: PC 에디터에서 다른 폰트로 입력하거나 워드/구글독스에서 붙여넣은 콘텐츠가 인라인 style로 저장돼 앱 서식을 뚫고 나오는 문제 — `.rich-text-content`에 폰트/크기/줄간격/색을 강제로 상속값으로 맞추는 규칙 추가(인라인 style을 이겨야 해서 예외적으로 `!important` 사용). 붙여넣은 리스트가 들여쓰기 없이 렌더링돼 불릿 마커가 박스 밖으로 나가던 것도 `ul/ol` 패딩 명시로 수정.

각 항목 Playwright로 개별 검증(컴퓨티드 스타일 확인 포함 — 예: 버튼 높이 4개 모두 56px 확인, glass-cta-primary의 backdropFilter/background 값 직접 확인) 후 커밋. 콘솔 에러 없음, `npm run build` 매 라운드 통과.

## 18. §17 이후 캘린더 리스트뷰 정렬·라벨 정리 + 아이콘 버튼 색상/블러 마감 (10차 라운드)

짧은 마무리 라운드. 세 건 모두 독립적으로 검증 후 반영.

- **캘린더 리스트뷰 날짜 라벨/정렬**: 날짜 배지가 "일정" 라벨 + "{day}일" 형태의 2줄 구성이었는데, 리스트 자체가 이미 "일정표"이므로 "일정"/"일"이 중복 워딩이라는 지적에 따라 순수 숫자만 남기고 `w-11 h-11` 원형 박스에 중앙 정렬. 정렬 순서도 데이터 등록 순서를 그대로 따르고 있어 날짜순이 아니었던 문제를 함께 수정 — 날짜 문자열을 뽑는 `getEventDateStr(item)` 헬퍼를 공용화하고 `monthEvents`에 `.sort((a, b) => getEventDateStr(a).localeCompare(getEventDateStr(b)))`를 추가해 임박한 일정 순으로 리스트업되도록 함.
- **전체 리스트 기획안 아이콘 버튼 톤 변경**: 이모지를 📄→📋로, 배경을 흰색 계열(`.glass-cta` + `.glass-cta-strong`)에서 서류 봉투/크래프트지를 연상시키는 갈색·주황 사이 톤으로 변경 — `globals.css`에 `.glass-cta-kraft`(`rgba(180, 108, 48, 0.4)` 배경, 연한 크림색 보더·쉐도우, 기존 글래스 클래스와 동일하게 `-webkit-backdrop-filter`를 표준 속성보다 먼저 선언) 신규 작성해 적용.
- **비활성 Drive 아이콘 버튼 블러 누락 수정**: 완성본이 없는 콘텐츠를 선택했을 때 뜨는 비활성 Drive 버튼이 `bg-slate-300/50`뿐이라 블러가 전혀 없이 뒷배경이 그대로 비쳐 보이는 문제 — 다른 글래스 버튼들과 재질이 어긋나 있었다. `globals.css`에 `.glass-cta-disabled`(중성 회색 `rgba(148, 163, 184, 0.38)` + `backdrop-filter: blur(10px)`, `@supports not` 폴백 포함)를 신규 작성해 교체, 비활성 상태에서도 실제 블러가 적용되도록 함.

Playwright로 402×874 뷰포트에서 확인: 캘린더 리스트뷰 날짜 배지 텍스트가 `04`/`06`/`07`/`10`/`13`/`14`/`14`/`17`/`17`/`18`처럼 순수 숫자만 오름차순으로 표시됨을 확인(더 이상 "일정"/"일" 없음). 전체 리스트에서 항목 선택 시 `.glass-cta-kraft` 버튼의 `getComputedStyle().backdropFilter`가 `"blur(10px)"`로 실제 블러 적용됨을 확인, 내부 `<span>`의 코드포인트가 `1f4cb`(📋)임을 별도 확인(스크린샷에서 이모지가 빈 사각형으로 찍힌 것은 캡처 타이밍상 폰트 아티팩트였고 DOM/렌더 자체는 정상). 완성본 미업로드 항목 선택 시 `.glass-cta-disabled` 버튼도 `backdropFilter: "blur(10px)"`로 확인(기존 `bg-slate-300/50`는 `"none"`이었음). 콘솔 에러 없음, `npm run build` 통과.

## 19. §18 이후 아이콘 버튼 색상/불투명도 및 리스트 선택 상태 강조 (11차 라운드)

- **기획안 아이콘 버튼 색상 재조정**: §18에서 넣은 크래프트지 갈색이 "너무 어두워 보인다"는 피드백 — 갈색 대신 앱 전체에서 기획안을 나타낼 때 일관되게 써온 `#FFB800` amber(`.glass-badge-proposal`, 캘린더 이벤트 바와 동일 색)로 `.glass-cta-kraft`의 배경색을 교체. 배경 불투명도도 0.4→0.55로 올려 더 또렷하게 보이도록 함(클래스명 `glass-cta-kraft`는 유지, 값만 amber로 교체 — 리네이밍은 범위 밖으로 판단).
- **완성본(Drive) 아이콘 버튼 불투명도**: 비활성(완성본 없음) 상태의 `.glass-cta-disabled`도 0.38→0.55로 상향. 활성 상태는 기존 `.glass-cta-primary`(완성본 업로드/보기 텍스트 버튼과 공유하는 재질, 0.38)를 그대로 쓰면 다른 버튼들의 톤까지 함께 바뀌므로, 이 아이콘 버튼 전용으로 `.glass-cta-primary-strong`(0.55) 모디파이어를 신규 작성해 `glass-cta-primary`와 함께 적용 — `.glass-cta-strong`과 같은 패턴. 구현 중 두 클래스가 동일 우선순위(단일 클래스 셀렉터)라 소스 순서상 나중에 오는 규칙이 이긴다는 걸 놓쳐, 처음엔 `-strong` 규칙을 `.glass-cta-primary`보다 앞에 둬 값이 먹지 않는 버그가 있었다 — `.glass-cta-primary` 블록 뒤로 옮겨 해결.
- **전체 리스트 선택 상태 강조**: 선택된 항목이 테두리/링만으로는 눈에 덜 띈다는 피드백 — 카드 배경을 `bg-white`→(선택 시) `bg-[#EAF2FF]`(연한 파랑)로, 제목 텍스트를 `text-slate-900`(검정에 가까움)→(선택 시) `text-[#002454]`(짙은 남색, 기존 테두리/링과 같은 색)로 변경. 부제(작성자·팀 정보)는 원래도 회색이라 "검정 텍스트" 대상이 아니므로 변경하지 않음.

Playwright로 확인: 선택된 항목의 `getComputedStyle().backgroundColor`가 `rgb(234, 242, 255)`(#EAF2FF), 제목 색이 `rgb(0, 36, 84)`(#002454)로 반영됨을 확인. `.glass-cta-kraft` 배경이 `rgba(255, 184, 0, 0.55)` + `backdropFilter: blur(10px)`, 비활성 Drive 버튼이 `rgba(148, 163, 184, 0.55)`, 활성 Drive 버튼(완성본 있는 항목으로 전환 확인)이 `rgba(0, 36, 84, 0.55)`로 각각 확인 — 카스케이드 순서 수정 전에는 활성 버튼이 `0.38`(base `.glass-cta-primary` 값)로 나와 버그를 실제로 잡아냄. 콘솔 에러 없음, `npm run build` 통과.

## 20. §19 이후 비활성 Drive 버튼 권한 게이팅 + CTA 텍스트 볼드 제거 (12차 라운드)

- **비활성 Drive 버튼 노출 조건 세분화**: 완성본이 없는 콘텐츠를 선택했을 때 뜨는 비활성 Drive 버튼을 무조건 노출하던 것을, 열람자의 권한에 따라 분기하도록 변경 — 해당 콘텐츠의 관리자 또는 작성자(수정 권한 보유자)에게는 기존처럼 비활성 상태로 노출하되, 그런 권한이 없는 단순 열람자에게는 완성본이 없을 때 버튼 자체를 아예 렌더링하지 않음(완성본이 이미 있으면 권한과 무관하게 항상 노출 — 열람 자체는 누구나 가능해야 하므로). 권한 판정은 `src/app/actions/content.ts`의 삭제 권한 체크와 동일한 관리자 기준(`user.email === 'admin@admin.com'` 또는 `user.user_metadata?.is_admin === true`)에, `MobileDetailModal`의 기존 `isOwnContent` 패턴과 동일한 작성자 이메일 비교(`item.content_body`를 파싱한 `authorEmail`과 로그인 사용자 이메일 일치 여부)를 더해 재사용 — 코드베이스에 이미 있던 두 기준을 그대로 가져와 새 위치(`MobileShell.tsx`의 전체 리스트 액션 바)에 적용한 것이라 새로운 권한 개념을 만들지 않았다.
- **CTA 버튼 텍스트 볼드 제거**: "기획안 작성"/"완성본 업로드" 버튼의 `font-black`(900)을 `font-normal`(400)로 변경.

Playwright 검증: 두 버튼 텍스트의 `getComputedStyle().fontWeight`가 `"400"`으로 확인. 권한 게이팅은 이 환경에 admin 테스트 계정 하나만 존재해 "권한 없는 열람자" 분기를 실제 로그인으로 직접 재현하지는 못했다 — 대신 `isAdmin`/`isOwnContent`/`canManage` 판정 로직을 Node로 분리해 관리자/본인/타인(권한 없음)/작성자 정보 없는 레거시 콘텐츠 네 가지 입력 조합으로 단위 검증했고, admin 계정으로는 완성본 있는 항목(활성 버튼 노출)·없는 항목(admin이라 canManage=true로 비활성 버튼 그대로 노출) 두 경우 모두 회귀 없이 기존과 동일하게 렌더링됨을 확인했다. 콘솔 에러 없음, `npm run build` 통과.

## 21. §20 이후 대시보드 승인대기 뱃지 정리 + 완성본 업로드 버튼 색상 (13차 라운드, 일부 보류)

- **대시보드 "승인 대기 중" 항목 뱃지 정리**: 각 항목 좌측의 "기획안"/"완성본" 텍스트 뱃지와 우측의 원형 아이콘(완성본 `+`/기획안 `!`)을 모두 제거. 우측 자리에는 전체 리스트·캘린더와 동일한 패턴으로 완성본이 실제로 업로드(`isFinal && hasDriveLink`)됐을 때만 Google Drive 아이콘을 표시하도록 교체.
- **"완성본 업로드" 버튼 색상**: 기존 짙은 네이비(`.glass-cta-primary`)가 너무 어둡다는 피드백 — 이 버튼 전용으로 `.glass-cta-sky`(하늘색 계열 `rgba(56,189,248,0.55)`)를 신규 작성해 적용. 배경이 밝아진 만큼 흰 텍스트 대신 "기획안 작성" 버튼과 같은 짙은 네이비 텍스트(`#002454`)로 바꿔 대비를 유지(대비비 계산상 약 9.5:1로 충분). `.glass-cta-primary`는 다른 곳(Drive 상세보기 버튼, 상세보기 닫기 버튼)에서 계속 쓰이므로 그대로 두고, 이 버튼에만 별도 클래스를 만들어 영향 범위를 좁혔다.
- **"다른 사람들의 콘텐츠 보기" 블록 재구성 요청 — 보류**: 사용자가 지적한 위치(승인 대기 중 바로 아래)는 코드상 "프리뷰 캐러셀" 블록과 일치한다(Figma 조사 기록상 대시보드 메인위젯 `863:146804` 내부 서브컴포넌트, §2.2 참고). 이 세션은 Figma에 쓰기는커녕 다시 읽기 조회조차 할 수 있는 도구가 연결되어 있지 않아(이전 라운드에서 확인됨) 사용자가 요청한 "피그마에서 찾아서 다시 구성"을 이번 라운드에서 수행하지 못했다 — 사용자에게 Personal Access Token을 요청한 상태. 조사 중 참고가 될 만한 사실 하나 발견: PC 버전의 대응 기능(`src/components/OtherProposalsCarousel.tsx`, "다른 사람들의 기획안")은 실제로는 완성된 캐러셀 UI가 전부 구현되어 있음에도 컴포넌트 최상단에서 조건 없이 "기능 준비 중" 잠금 오버레이만 반환하도록 되어 있어(그 아래 실제 캐러셀 코드는 도달 불가능한 죽은 코드), 현재 PC에서도 이 기능이 의도적으로 비활성 상태다.

이번 라운드는 Playwright로 확인하려던 중 dev 서버의 HMR이 이번에 추가한 `.glass-cta-sky` 클래스만 반영하지 않는 현상을 발견(같은 라운드의 JS/TSX 변경은 정상 반영됨, `npm run build`는 통과) — 소스 파일 자체는 문법 오류 없이 정상(중괄호 균형 확인)이라 코드 문제는 아니고 dev 서버 쪽 캐시/워처 이슈로 판단, 사용자에게 재시작 여부를 확인했다. 사용자는 이미 실시간 미리보기에서 정상 반영된 것을 직접 확인했다고 답변 — 새로 페이지를 불러오는 Playwright/curl 검증과 달리, 이미 열려 있던 브라우저 탭은 HMR 웹소켓으로 변경사항을 바로 받는 것으로 보인다(재시작은 하지 않음). 이후 라운드부터는 이 차이를 감안해, CSS 전용 변경은 소스 코드 직접 확인 + 가능하면 시간을 두고 재검증하는 방식을 병행했다.

## 22. §21 이후 색상 재조정 · 캘린더 팝업 재구성 · GNB 정리 · 권한별 액션바 마무리 (14차 라운드)

같은 턴 안에서 여러 메시지가 연달아 도착해 순서대로 처리. 이 라운드부터 앱 곳곳의 파란색 계열을 대시보드 상단 "기획안 마감" D-day 위젯의 기존 색상(`#C0CFE4` 배경 / `#003378` 텍스트, 이미 대시보드에 있던 톤)으로 통일하는 방향이 잡혔다.

- **"완성본 업로드" 버튼 색상 2차 수정**: 1차로 넣은 하늘색(sky-400)이 "생각보다 너무 밝다"는 피드백 — `.glass-cta-sky`를 `#C0CFE4`/0.85 배경 + `#003378` 텍스트로 재조정(대비비 약 8:1). 같은 색상 쌍을 이후 항목들에도 일관되게 재사용.
- **캘린더 전역 파란색 스윕**: 연/월 선택 드롭다운 포커스 링, "Today" 버튼, 요일 헤더의 토요일 색, 월간 그리드 선택된 날짜의 배경/링, 리스트뷰·날짜팝업 카드의 호버 색, 날짜팝업 내 팀 아바타 배지까지 전부 Tailwind 기본 `blue-*`에서 `#C0CFE4`/`#003378` 쌍으로 교체. Google Drive 아이콘 컨테이너의 `text-blue-700`(실제로는 SVG가 자체 fill을 갖고 있어 시각적으로 무의미한 값)과 날짜팝업 닫기 버튼의 `hover:bg-blue-900`(이미 짙은 네이비라 "밝은 하늘색"에 해당하지 않음)은 대상에서 제외.
- **캘린더 날짜팝업 재구성**: 이전 조사 기록(§2.2, 캘린더2/3)에 남아있던 "카드가 화면을 꽉 채우지 않고 다음/이전 날짜 카드가 옆으로 살짝 비쳐 보이는 peek 카러셀" 구조를 뒤늦게 반영 — 기존엔 각 날짜 슬라이드가 `w-full`이라 peek 없이 완전히 꽉 찬 카드였다. 슬라이드 폭을 `calc(100% - 6rem)` 고정값으로 바꿔 남는 6rem이 좌우로 자연스럽게 peek되게 하고, 이 폭에 맞춰 `scrollPopupTo`/`handlePopupScroll`도 `clientWidth` 나눗셈 대신 실제 자식 요소 위치 기반으로 다시 짰다(퍼센트 padding과 퍼센트 width를 같이 썼던 첫 시도는 계산 기준이 서로 달라(부모 vs 컨테이너 content box) 의도한 80%가 아니라 64%로 축소되는 버그가 있어 고정 단위로 전환해 해결). 배경의 Dim 레이어도 검정(`bg-black/60`)에서 흰색(`bg-white/75`)으로 변경.
- **GNB "PC 뷰" 버튼 삭제**: 프로필 화면에서 이미 접근 가능해 중복이라는 판단으로 완전 제거.
- **전체 리스트 완성본 액션 버튼 마무리**: 완성본이 없을 때 비활성 Drive 아이콘을 보여주던 것을 다시 손봤다 — 수정/업로드 권한이 있는 사람(관리자·작성자)에게는 이제 비활성 아이콘 대신 곧장 업로드로 연결되는 활성 버튼(📤, `.glass-cta-sky`)을 보여주고, 권한 없는 열람자에게는 여전히 버튼 자체를 숨긴다. 더 이상 쓰이지 않게 된 `.glass-cta-disabled`는 grep으로 참조 0건 확인 후 삭제.
- **대시보드 "승인 대기 중" 배경색 — 확인 안 된 피드백 강조**: 크루원이 남긴 콘텐츠 중 아직 대응하지 않은 피드백이 있는 항목은 진한 노란색(`amber-200`), 피드백이 없거나 이미 확인 후 답글·수정(재제출)까지 마친 항목은 흰색 배경으로 구분. 별도의 읽음/안읽음 저장 기능을 새로 만들지 않고, PC 관리자 페이지(`dashboard/page.tsx`, `api/notifications/route.ts`)가 이미 쓰고 있던 판정 — `feedback_comment`가 비어있지 않거나 `status`가 수정요청 계열(`revision`/`final_revision`)이면 미해결 피드백으로 간주 — 을 그대로 재사용했다. 크루원이 수정 후 재제출하면 `AdminStatusManager.tsx`의 기존 로직에 따라 status가 `revision`에서 벗어나므로, 새 저장소 없이도 "이미 확인 후 대응함"이 자연스럽게 표현된다.

Playwright 검증: sky 버튼 배경이 `rgba(192, 207, 228, 0.85)`로 확인(첫 시도 때 겪었던 dev 서버 HMR 지연은 이번엔 재현되지 않음). 캘린더 팝업에서 슬라이드 폭/컨테이너 폭 비율이 약 0.739로 확인(고정 단위 전환 전 버그였던 0.64에서 개선, 스크린샷으로도 다음 날짜 카드가 오른쪽에 실제로 비쳐 보임을 확인), Dim 레이어가 `oklab(0.999994 ... / 0.75)`(≈흰색 75%, Tailwind v4가 알파 있는 색을 oklab으로 직렬화)로 확인. 전체 리스트에서 완성본 없는 항목 선택 시 `.glass-cta-sky` 업로드 버튼이 실제로 나타나고 `.glass-cta-disabled`는 페이지 전체에서 0건임을 확인. 대시보드 배경색 로직은 Node 단위 테스트로 5가지 입력 조합(수정요청 상태/피드백 텍스트 있음/둘 다 없음 등) 전부 정답 확인 — 실제 DB를 직접 조회해보니 현재 승인대기 항목 중에는 미해결 피드백이 있는 항목이 하나도 없어(전부 `feedback_comment`가 `null`/빈 문자열이고 상태도 `approved`/`final_submitted`) 화면상으로는 전부 흰색으로만 보였는데, 이는 로직 문제가 아니라 현재 데이터 상태임을 실제 쿼리로 확인했다. 콘솔 에러 없음, `npm run build` 통과.

## 23. §22 이후 Figma 접근 재개, 완성본 업로드 버튼 텍스트, 캘린더 리스트뷰 선택 통합, 하단 검색 위젯 이전 (15차 라운드)

이 라운드 시작 시점에 사용자가 "예전에 제공한 read 전용 Personal Access Token이 아직(7일간) 유효하니 그걸 쓰라"고 안내 — 이번 세션 자체에는 그 토큰이 없었지만, 과거 세션 스크래치패드 디렉터리(같은 로컬 머신, 같은 사용자 계정 하에 남아있던 이전 세션들의 임시 폴더)를 뒤져 `.figma_token` 파일로 저장돼 있던 것을 찾아 재사용했다. `GET /v1/me`는 스코프 부족(`file_content:read`만 있고 `current_user:read` 없음)으로 403이 났지만, 파일 노드 조회(`GET /v1/files/:key/nodes`)는 정상 동작해 실제로 이번 라운드 조사에 사용할 수 있었다(문서에 토큰 값 자체는 기록하지 않음 — git에 커밋되는 파일이라 보안상 제외).

- **검색 돋보기를 상단에서 하단으로 이동**: Figma REST API로 `852:34431`("bottom navbar" 컴포넌트) 원본을 직접 조사한 결과, 4탭 캡슐(287×58)과 정사각형 검색 위젯(58×58)이 8px 간격으로 나란히 배치된 하나의 그룹이었음을 확인(캡슐 높이 58px과 검색 위젯 한 변이 정확히 같다는 것도 확인) — 이 비율을 그대로 적용해 하단 nav를 `flex-1` 캡슐 + `w-[3.625rem] h-[3.625rem]` 원형 버튼(`gap-2`=8px)으로 재구성. 같은 조사에서 대시보드 화면(`863:168576`) 최상단에 로고/타이틀/알림 벨에 해당하는 요소가 Figma 원본에 아예 없다는 것도 확인(상태바 아래 흐릿한 블러 스트립뿐) — 상단 `<header>`를 완전히 제거하고 `<main>`의 상단 패딩도 헤더 높이 보정값에서 safe-area만큼으로 줄였다. 검색 버튼의 클릭 로직(리스트 탭 전환 + 검색 트리거 증가)은 그대로 유지.
- **검증 중 발견한 별도 버그 수정**: 새 위치의 검색 버튼을 다른 탭(대시보드 등)에서 처음 누르면 전체 리스트로는 이동하지만 검색창이 펼쳐지지 않는 현상을 발견 — `MobileFullList`가 이 시점에 처음 마운트되면서 `revealSearch` prop이 곧장 참(truthy) 값으로 들어오는데, 개발 모드의 React Strict Mode가 마운트 직후 effect를 정리→재실행 한 번 더 시뮬레이션하면서 토글이 두 번 걸려 결국 안 열린 것처럼 보이는 버그였다(이미 리스트 탭에 있는 상태에서 다시 누르는 경우는 신규 마운트가 아니라 이 이중 실행이 없어 문제없이 동작했었다 — 그래서 이전 라운드들에서는 안 드러났던 것으로 보임). 처리한 `revealSearch` 값을 `ref`로 기억해 같은 값에 대한 두 번째 실행을 무시하도록 멱등하게 고쳤다.

Playwright 검증: 헤더 텍스트("연세 미디어센터")와 벨 아이콘 0건 확인, 검색 버튼 바운딩박스가 `x=328,y=804,58×58`, nav 캡슐이 `x=16..320`으로 정확히 8px 간격 확인. 새 위치 검색 버튼을 대시보드 탭에서 곧장 눌러도 전체 리스트로 이동 + 검색창이 정상적으로 펼쳐지고 실제로 포커스까지 이동함을 확인(수정 전에는 `max-h-0`로 접힌 채였음). 완성본 없는 항목의 업로드 버튼 텍스트가 "완성본 업로드"로 확인. 캘린더 리스트뷰에서 항목 선택 시 배경색 `rgb(234, 242, 255)`(#EAF2FF)과 `.glass-cta-kraft` 버튼 노출 확인. 콘솔 에러 없음, `npm run build`(TypeScript 포함) 통과.

## 24. §23 이후 하단 액션바 버튼 폭 통일 및 높이 축소 (16차 라운드)

- **버튼 폭 불일치 진단**: "기획안 작성/완성본 업로드"(둘 다 아이콘+텍스트) 조합은 각각 181px로 고르게 나뉘는데, "📋/완성본 업로드"(아이콘 전용 vs 아이콘+텍스트) 조합은 165px/197px로 나뉘어 있었다. `flex-1`(= `flex: 1 1 0%`)과 `min-w-0`이 둘 다 걸려 있으면 이론상 내용물과 무관하게 정확히 반반 나뉘어야 하는데, 실측(`getComputedStyle`/`getBoundingClientRect`)해보니 실제 원인은 그게 아니라 **패딩 비대칭**이었다 — 아이콘 전용 버튼(`📋`, 완성본 상세보기 Drive 아이콘)은 패딩이 아예 없고, 텍스트가 있는 버튼(완성본 업로드/기획안 작성)만 `px-4`가 있어서, 양쪽 패딩을 똑같이 0으로 맞추면 즉시 정확히 181/181로 나뉘는 것을 확인했다(반대로 `min-w-0` 유무는 실측상 폭에 변화가 없었다 — 애초에 원인이 아니었음). 두 아이콘 전용 버튼에도 텍스트 버튼과 같은 `px-4`를 추가해 다섯 가지 버튼 변형(기획안 작성/완성본 업로드/📋/완성본 상세보기 Drive/완성본 업로드-아이콘행) 전부가 항상 정확히 반반 나뉘도록 통일 — 향후 유지보수자를 위해 이 패딩-대칭 요구사항을 코드 주석으로 남겨뒀다.
- **버튼 높이 3/4 축소**: 다섯 변형 전부 `h-14`(56px) → `h-[2.625rem]`(42px, 정확히 3/4)로 통일.

Playwright 검증: 네 가지 조합(대시보드 미선택, 전체 리스트 완성본 있음, 전체 리스트 완성본 없음, 캘린더 리스트뷰) 전부에서 두 버튼이 정확히 181px/181px, 높이 42px로 동일함을 확인. 스크린샷으로도 육안 확인. 콘솔 에러 없음, `npm run build` 통과.

## 25. §24 이후 대시보드 프리뷰 캐러셀 Figma 재구성 (17차 라운드)

보류돼있던 "다른 사람들의 콘텐츠 보기"(프리뷰 캐러셀, `863:151021` "미리보기 스와이프" 인스턴스) 재구성을 Figma REST API로 직접 조사해 진행했다.

**조사 결과**: 392×224 흰 카드(반경 15px, 부드러운 드롭섀도우)에 좌측 썸네일(126×202, 이미지 채움, 반경 7px)과 우측 콘텐츠 컬럼(225×202)으로 구성. 좌측 썸네일 하단에 좌우 화살표 버튼이 나란히(기존 구현은 우상단에 세로로 쌓여있었음). 우측 컬럼은 위에서부터: 아바타(28×28)+이름+역할 한 줄씩, "›" 화살표 힌트, 제목, 해시태그, 기획 의도 본문 스니펫, 그리고 맨 아래 좋아요/댓글 수 버튼 2개(각각 트랜스페어런트/`#99B3D6` 배경, `#003378` 텍스트 — 둘 다 기존 앱에서 이미 쓰던 브랜드 컬러와 정확히 일치). 텍스트 콘텐츠(작성자 "21기 현나리", 역할 "인스타 팀장", 제목 "3D 프린팅...", 해시태그, 본문)가 PC의 잠겨있는 "다른 사람들의 기획안"(`OtherProposalsCarousel.tsx`) 컴포넌트의 `DEFAULT_PROPOSALS` 목업 데이터와 완전히 동일 — 이 두 컴포넌트가 같은 디자인 의도(다른 사람의 기획안을 소셜하게 둘러보는 기능)에서 나온 것임을 확인했다. 폰트 크기는 Figma 원본이 5.6~11.2px로 매우 작게 잡혀있었는데, 실제 폰(1x)에서는 가독성이 떨어질 값이라 앱의 기존 타입 스케일에 맞춰 적당히 키워 적용(비율/위계는 그대로 유지 — 제목 > 이름 ≈ 본문 > 해시태그).

**반영 내용**:
- 화살표를 썸네일 하단 좌우 배치로 이동.
- 아바타/이름 줄을 "이름 + 소속" 2줄 스택으로 재구성, 우측에 작은 "›" 힌트 아이콘 추가.
- 기획 의도(`intent`, HTML 태그 제거 후 2줄 클램프) 미리보기 신규 추가 — 기존엔 제목/해시태그까지만 있었음.
- **좋아요 버튼은 제외**: Figma에는 있었지만 앱에 좋아요 기능 자체가 없고(스키마에 관련 컬럼 없음), PC의 대응 기능도 좋아요 수를 해시값으로 지어내는 가짜 데이터라 "기능 준비 중"으로 잠가둔 상태였다 — 없는 데이터를 지어내지 않기 위해 이 버튼은 넣지 않았다.
- **댓글/피드백 수 배지는 실제 데이터로 추가**: `content_body`를 파싱한 `discussions` 배열의 실제 길이를 사용(가짜 수치 아님).
- **"기획안 보기"/"완성본 보기" 텍스트 버튼 제거**: 이전 세션에서 추가됐던 것으로, §11 감사 기록에도 "Figma 어디에도 없는" 요소라고 이미 명시돼 있었다. 카드 전체(썸네일+콘텐츠 영역)가 이미 탭하면 peek 미리보기로 연결되므로 기능 중복이기도 해서, Figma에 실제로 있던 피드백 수 배지로 교체하며 함께 정리했다. 더 이상 쓰이지 않는 `onOpenDetail` prop은 `MobileDashboard`에서 제거.

Playwright 검증: 카드 스크린샷으로 썸네일 하단 화살표, 아바타/이름/소속/화살표 힌트, 제목, 해시태그, 기획 의도 스니펫, "💬 0" 피드백 배지, 점 인디케이터까지 전부 의도대로 렌더링됨을 확인. 카드 탭 시 peek 미리보기(배지 "기획안 📝", 작성자 칩, 제목(가제) 카드 등)가 정상적으로 열림을 스크린샷으로 확인(텍스트 셀렉터 기반 자동 체크는 타이밍 이슈로 false negative가 있었으나 스크린샷상 실제로는 정상 동작). "기획안 보기"/"완성본 보기" 버튼 0건 확인. 콘솔 에러 없음, `npm run build`(TypeScript 포함) 통과.

## 26. §25 이후 완성본 업로드 실제 연결 + 제출/취소 버튼 정리 (18차 라운드)

**완성본 업로드가 특정 콘텐츠에 실제로 연결되도록 수정**: 지금까지 `MobileSubmitModal`은 기획안이든 완성본이든 항상 `contents` 테이블에 새 행을 `insert`했다 — 즉 "이 콘텐츠의 완성본 업로드" 버튼을 눌러도 실제로는 그 콘텐츠와 아무 관계 없는 새 글이 만들어졌다(세션 초반부터 "수정하기가 진짜 수정이 아니다"로 이미 알려져 있던 제약과 같은 원인). PC의 대응 컴포넌트(`FinalSubmitForm.tsx`)를 다시 읽어 정확한 필드 매핑을 확인 후 그대로 이식:
- 새 `targetItem` prop 추가 — 있으면(`mode==='final' && targetItem`, `isAttachingFinal`) 새 글을 만들지 않고 `targetItem.id`를 `.eq()`로 지정해 **업데이트**한다. `content_body`는 기존 값을 스프레드로 보존한 채 `postContent`/`finalKeywords`/`finalCrew`/`finalDescription`/`finalSubmittedAt`만 갱신(PC `FinalSubmitForm.handleSubmit`과 완전히 동일한 키 이름), `final_url`과 `status: 'final_submitted'`도 함께 업데이트.
- 폼 필드도 완성본 전용으로 재구성: 제목/콘텐츠 분류 입력 대신 "완성본을 업로드할 콘텐츠" 읽기 전용 참조 카드(대상 제목/팀/유형)를 보여주고, "기획 의도 및 배경" 필드는 완성본 전용 새 상태 `postContent`(본문/캡션 내용)로, "구성 및 내용 설명"은 "비고"(`finalDescription`)로 재라벨링. 기획안 전용 개념인 "촬영 계획"·"데드라인"은 이 모드에서 숨김.
- 이미 완성본이 있는 콘텐츠를 다시 열면(재제출/수정) PC와 동일하게 기존 `postContent`/`finalDescription`/`finalKeywords`/`finalCrew`/`final_url`로 폼을 프리필한다.
- 호출부 3곳에서 대상 아이템을 넘기도록 연결: 전체 리스트/캘린더 리스트뷰 선택 시의 업로드 버튼(`handleOpenSubmit('final', item)`), 상세보기 배지 탭(`onEdit`을 거쳐 이미 `item`을 넘기고 있었는데 셸에서 그동안 버려지고 있었음), 상세보기 "수정하기" 버튼(같은 `onEdit` 경로라 자동으로 함께 연결됨 — 다만 `mode==='proposal'`일 때는 여전히 새 글을 만드는 기존 동작 그대로임, 기획안 수정 자체를 진짜로 만드는 건 이번 범위 밖). 대시보드/전체 리스트의 범용 "완성본 업로드"(아무것도 선택 안 한 상태의 CTA)는 대상이 없으므로 기존처럼 새 글 생성 유지.

**제출/취소 버튼 위치 교환 + 미저장 변경 확인**: 하단 액션바에서 "제출하기"(넓은 `flex-1`)와 "취소"(좁은 `w-1/3`)의 좌우 위치를 서로 바꿨다(각 버튼 자체의 크기는 그대로 — 자리만 교환). 취소 버튼에 `handleCancel`을 새로 연결해, 폼이 열릴 때의 초기값(신규 작성이면 빈 값, 완성본 프리필이면 그 프리필 값)을 스냅샷으로 저장해두고 취소 시점의 현재 값과 비교 — 하나라도 다르면 `window.confirm`으로 "변경 사항이 있습니다. 저장하지 않고 나가시겠습니까?"를 띄우고, 취소(머무름)를 선택하면 닫지 않는다. 헤더의 X 버튼과 스와이프-다운-닫기 제스처는 이번 요청 범위(취소 버튼)가 아니라서 그대로 즉시 닫히는 기존 동작 유지 — 필요하면 후속으로 통일 가능.

Playwright 검증: 완성본 없는 항목을 선택해 업로드 버튼을 누르면 그 항목 제목/팀/유형이 적힌 참조 카드가 뜨고, "촬영 계획"/"데드라인" 라벨이 0건, 필드 라벨이 "본문 / 캡션 내용"/"비고"로 바뀌어 있음을 확인. 하단 버튼 순서가 "완성본 업로드하기 ➔"(flex-1, 좌) → "취소"(w-1/3, 우)로 바뀐 것을 확인. 본문 필드에 텍스트를 입력한 뒤 취소를 누르면 실제로 confirm 다이얼로그("변경 사항이 있습니다...")가 뜨는 것을 확인. 실제 DB 업데이트(새 글이 아니라 기존 행이 갱신되는지)는 실제 콘텐츠 데이터를 건드리게 되어 이번엔 실행하지 않았고, 대신 PC `FinalSubmitForm.tsx`의 검증된 패턴과 필드명을 1:1로 대조해 코드 정확성을 확인했다. 콘솔 에러 없음, `npm run build`(TypeScript 포함) 통과.

## 27. §26 이후 캘린더 날짜팝업 실제 재조사 반영 (19차 라운드)

"캘린더에서 특정 콘텐츠를 눌렀을 때 나오는 화면을 피그마에서 찾아서 그 UI로 구현" 요청으로, 이전 라운드(§22)에서 인터랙션 그래프 기록만 근거로 재구성했던 날짜팝업을 이번엔 Figma REST API로 실제 프레임을 직접 조회해 재검증·재반영했다.

**조사 경위**: 처음 조회한 `863:18256`("캘린더 팝업" 컴포넌트)은 페이지 최상위에 캘린더 섹션과 별개로 떠 있어 실제 사용되는 프레임이 아닐 가능성이 있었다 — `캘린더` 섹션(`863:17012`)의 실제 자식 프레임을 다시 조회해 "캘린더 1(메인)"~"캘린더 7(완성본 상세보기)"이라는, §2.2 인터랙션 기록과 정확히 이름이 일치하는 프레임 7개를 찾았고, 그중 "캘린더 2(팝업)"(`841:80023`)을 실제 대상으로 확인했다.

**발견한 사실**:
- **카드더미(903×388) 구조 재확인**: 가운데 활성 카드(310×300)와 좌우 peek 카드(275×264, x=-249/379)로 구성 — §22에서 고정 단위로 고친 peek 카러셀 구조가 이 실측치와 방향상 일치함을 재확인(그대로 유지).
- **Dim은 원래 검정 40%**(`rgba(0,0,0,0.4)`)였다 — 하지만 사용자가 이전 라운드에서 "검정이 아니라 흰색으로" 명시적으로 요청해 변경한 값이라, 이번 조사로 원본이 검정이었다는 걸 알게 됐어도 사용자의 명시적 오버라이드를 되돌리지 않고 흰색 그대로 유지했다(대시보드 GNB 흰 배경 제거 때와 같은 원칙 — 사용자가 의도적으로 Figma와 다르게 요청한 값은 이후 조사로 "원본"이 다르게 나와도 존중한다).
- **날짜 항목 목록이 실제로는 컴팩트한 한 줄 행 리스트였다**: 지금까지 구현은 패딩이 큰 카드(원형 배지+기획안/완성본 필+제목+부제 세로 스택)였는데, 실제 Figma 컴포넌트(`863:18256`)는 한 행에 [플랫폼 아이콘+콘텐츠 유형 뱃지] · [굵은 제목 + 회색 "유형 - 작성자" 부제]를 가로로 배치하고, 그 아래에 별도로 "피드백" 행(회색 점 + 최근 피드백 미리보기 텍스트, 예시 데이터: "기획안 - 다른 기획안과 겹치는 것 같아요")을 구분선과 함께 붙이는 훨씬 컴팩트하고 정보 밀도 높은 구조였다.
- **"← today" 필**: 카드더미 아래에 오늘로 즉시 돌아가는 작은 캡슐 버튼이 있었다 — 지금까지 구현에 없던 요소.
- 콘텐츠 유형별 아이콘/뱃지 색상(롱폼 `#003378`, 숏폼 `#E6EBF2`, 카드뉴스 `#F59E0B`, 카드뉴스(블로그) `#047857`, 기사 `#D0EBDB`)까지는 그대로 옮기지 않았다 — 이미 앱 전체가 기획안(amber)/완성본(green) 2색 체계로 일관되게 정리돼 있는데(§19~§24 여러 라운드에 걸쳐 확정) 콘텐츠 유형별 5가지 색을 추가로 들여오면 색상 체계가 다시 흩어지므로, 기존 이모지 플랫폼 아이콘(🎬/📸/✍️/📄, FullList와 동일 로직)으로 대체.

**반영 내용**:
- 날짜팝업 안의 각 콘텐츠 행을 [아이콘+제목/부제+기획안·완성본 뱃지] 한 줄 + (실제 피드백이 있을 때만) 최근 피드백 미리보기 한 줄로 재구성. 피드백 텍스트는 `content_body.discussions` 배열의 마지막 항목에서 실제로 가져온다(가짜 데이터 아님) — 피드백이 없는 항목은 그 줄 자체를 표시하지 않는다.
- "← 오늘로 이동" 필 추가: 이번 달을 보고 있고, 오늘 날짜에 실제 콘텐츠가 있고, 지금 보고 있는 슬라이드가 오늘이 아닐 때만 노출.

Playwright 검증: 실제 날짜팝업을 열어 각 항목 행의 렌더링 텍스트를 그대로 덤프해, 피드백이 있는 항목(예: "기획안 - 적어주신 피드백 잘 검토해 보았습니다~...")은 실제 크루 피드백 전문이 미리보기로 붙어 나오고, 피드백이 없는 항목은 그 줄이 아예 없는 것을 확인 — 실데이터 연동이 실제로 동작함을 확인했다. "오늘로 이동" 필은 실제 DB를 조회해보니 오늘(2026-08-15)에 등록된 콘텐츠가 없어 라이브 화면에서는 뜨지 않는 것이 정상임을 먼저 확인한 뒤, 조건 로직 자체는 Node 단위 테스트로 4가지 케이스(같은 달/오늘 콘텐츠 있음/현재 슬라이드가 오늘 아님 → 노출, 오늘 슬라이드 보는 중 → 숨김, 오늘에 콘텐츠 없음 → 숨김, 다른 달 → 숨김) 전부 정답을 확인했다. 콘솔 에러 없음, `npm run build` 통과.

## 28. §27 이후 캘린더 팝업 스크린샷 대조 재조정, peek 스크롤 잠금, 대시보드 선택 통합 (20차 라운드)

사용자가 실제 Figma 프로토타입 스크린샷(전체 화면 캡처)을 직접 첨부해줘서, §27에서 API로 추론했던 것보다 훨씬 정확하게 대조하며 세 가지를 반영했다.

- **캘린더 날짜팝업 쉘 제거**: 스크린샷을 보니 헤더 바(화살표 2개+X)와 흰 카드로 감싼 "팝업 쉘" 구조가 아니라, 날짜/날씨 라벨이 카드 밖에 독립적으로 크게 떠 있고 하단 "닫기" 버튼도 아예 없었다 — 배경(Dim)을 탭하면 닫히고 "오늘로 이동" 필로 오늘 날짜 카드까지 스와이프해 돌아오는 구조. 헤더 바/닫기 버튼을 전부 제거하고, 흰 카드 스타일을 팝업 전체를 감싸던 바깥 셸에서 각 날짜 슬라이드 자신으로 옮겼다("하나의 블록이 하나의 날짜"). peek 마진도 스크린샷 속 화면 끝 살짝 걸치는 정도(대략 20px 안팎)에 맞춰 `calc(100% - 6rem)`→`calc(100% - 2.75rem)`으로 좁혔다. 배경 탭으로 닫히는 기존 동작을 유지하기 위해 새로 추가된 각 인터랙티브 요소(날짜 라벨, 카러셀, 오늘로 이동 필, 점 인디케이터, 빈 상태 카드)에 `stopPropagation`을 달았다.
- **상세보기 peek 상태 세로 스크롤 잠금**: "미리보기 도크는 고정이라 위아래 스크롤이 불가능"하다는 지적 — 지금까지 peek/full 상태 구분 없이 `overflow-y-auto`였던 것을 `viewState==='peek'`일 때만 `overflow-y-hidden`으로 바꿔, 미리보기 상태에서는 세로 스크롤이 아예 안 되도록 고정(좌우 스와이프로 기획안⇄완성본 전환은 그대로 동작). full로 펼쳐지면 다시 스크롤 가능.
- **대시보드 "승인 대기 중"을 전체 리스트와 동일한 선택 메커니즘으로 통합**: "롤백되었나요?" 질문에 대한 답 — 사실 이 섹션은 처음부터 선택 메커니즘이 적용된 적이 없었다(뱃지/아이콘 정리, 피드백 기반 배경색만 §21/§24에서 반영됐었음). 이번에 전체 리스트/캘린더 리스트뷰와 동일하게 탭하면 선택(연한 파랑 배경/네이비 테두리·텍스트, 미해결 피드백 노란 배경보다 우선)되고 셸 공용 하단 액션바가 뜨도록 `selectedItem`/`onSelectItem`을 `MobileDashboard`에도 연결, 하단 액션바의 아이콘-버튼 분기 조건에 `'dashboard'`를 추가.

Playwright 검증: 대시보드 항목 선택 시 배경 `rgb(234, 242, 255)`(#EAF2FF)와 `.glass-cta-kraft` 버튼 노출 확인. 캘린더 팝업에서 "닫기"/"✕" 버튼 0건, 배경 바깥 탭 시 정상적으로 닫힘, 스크린샷도 첨부 레퍼런스와 구조적으로 일치함을 확인. 상세보기를 peek로 열었을 때 해당 `<main>`의 `overflow-y`가 `hidden`으로 확인(펼치면 `auto`로 복귀하는 기존 동작은 유지). 콘솔 에러 없음, `npm run build` 통과.
